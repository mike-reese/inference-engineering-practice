D1 — event store and query path

Command center v2, decision prototype (throwaway). Practice repo devtools/frontend/prototypes/D1/. Data and stores under /mnt/ie-data/cc-v2-proto/.

The question

The command center draws one window of time at one zoom level: a millisecond inside one engine iteration, one whole request, or a whole run of 500 requests. Every draw asks the store the same kind of question: give me every event between two times, for these processes and threads, plus the links between them, or give me one number per bucket (GPU busy, copy bytes) for a graph. Where the events live decides how fast that answer comes back, whether new events can arrive while a view reads, and how much the devtools image grows.

  • A — one JSON file per run, loaded whole (how run.json works today).
  • B — SQLite per run, with an R*Tree index on time so a window query reads only the rows it needs.
  • C — DuckDB over Parquet: columnar files sorted by time; DuckDB skips row groups outside the window.
  • D — Perfetto trace processor over our events converted to a trace (Chrome JSON here), queried with its SQL.

All four hold the same rows and answer through one API shape: window(t0, t1, sources, process, thread), lanes(t0, t1), state_at(t), focus(t0, t1, process, thread), and the slicing queries. Every result is fingerprinted; a check mark means the option returned exactly the same rows as B.

Recommendation

Recommendation: C — DuckDB over Parquet, one sorted Parquet file per record kind per run (events, links, samples, profiles), queried through one small Python API in the backend and in iectl.

Why.

  • Slicing and wide windows decide it. At the 19.4 M-event synthetic load SYNTHETIC, the whole-run union busy time and the 10 ms busy buckets take about 0.4 s in C against 13–17 s in B and D Observed; clipped measures and ratios over a request take 45 ms (C) against 100–180 ms. The owner's BI-style questions (any cursor pair, grouped by process and iteration, clipped at the edges, unions not sums) are ad hoc aggregates, which is what a columnar engine is for.
  • Size. The synthetic set is 0.28 GB in C, 12.3 GB in B and 10.4 GB as a Perfetto JSON trace Observed. Every saved run stays small enough to keep.
  • Same rows, standard SQL. Window functions, recursive CTEs and least/greatest express clipping, gaps-and-islands union and bucket walks directly; every query returned exactly the rows B returned Observed. Agents and the backend use the same duckdb module or CLI; any number of readers can scan the files.
  • Fast enough for the narrow windows too. 1 ms and one-iteration windows answer in 5–60 ms at every scale Observed; slower than B's R*Tree (0.1–30 ms) but inside an interactive budget for a view that caches what it drew.

Limits, and what they cost.

  • Live append is by files. Each batch is a new immutable Parquet part (1.4 ms per 1,000 events Observed); readers see it by globbing, and the read slowed from 5.2 to 6.7 ms after 68 parts Observed. A run needs compaction at its end (merge the parts, sort by time). DuckDB's own database file allows one process only Observed, so it is not the live path. D7 decides the live path on top of this.
  • Point-in-time and link lookups are scans. "State of every process at t" takes 220 ms at 19.4 M events (B: 5 ms) and a focus with its links 145 ms (B: 10 ms) Observed SYNTHETIC; both scan, because Parquet has no index, only per-row-group min/max. Scrubbing a cursor at 220 ms per step feels slow. Remedies, not built: precompute per-lane "last event before t" checkpoints at import; keep a second links file sorted by to_id.
  • +66 MB in the devtools image (duckdb==2.0.0); the import needs a way to build Parquet (this prototype used pyarrow, +166 MB more) Observed.

Why not the others. A loads the whole file for every question: 1.9 s at one run, 11.6 s and 6.3 GB resident at 1.9 M events, and an append rewrites the whole file (6.8 s at one run) Observed; the full synthetic set does not fit in this machine's memory Calculated. B is the best at narrow windows, instant state and live writes with concurrent readers (WAL, 8 ms per 1,000-event commit, readers unaffected Observed) and adds no dependency, but wide aggregates are 30–40× slower than C at scale (whole-run union 16.6 s vs 0.42 s), files are 44× larger, and its planner needed two hints (unary +, CROSS JOIN) to use the time index and to drive the link join from the focus rows (134 → 9 ms, 960 → 10 ms) Observed. D gives Perfetto's model for free, but loading takes 120 s and 18 GB resident at 19.4 M events, it has no append, and the conversion loses fidelity: 7.3 % of links bound to the wrong slice (v1 flow events bind by timestamp) at every scale, 1,021 CUDA-event instants dropped on the real run, and off-clock profiles have no home Observed. Exporting to Perfetto for ui.perfetto.dev stays useful as an output, not as the store.

Decision needed (owner): C alone, or C for recorded runs plus B (SQLite WAL) as the live buffer that is compacted into Parquet at run end. The second answers instant state and live reads fastest but means two stores and two query paths; this prototype does not settle it, and D7 (live path) is where it is measured.

Problems found in the existing data and code (reported, not fixed)

  1. Timeline run e08b8b: a 9.4 s gap at the end of the measured request. The last GPU work of iteration 129 ends 0.404 s after client send, but the final stream event reaches the client at 9.778 s; the request in executor and decode (iterations 67-129) spans include the gap. Observed Cause not established; Inferred: the profiler stopping after iteration 129 (profile_range 1-129) stalls the process while Nsight flushes. Any "whole request" window or end-to-end latency on this run includes it.
  2. The Nsight import allow-list drops most of the capture (adapters/nsys.py): of 89,366 Nsight events and 1,111,650 GPU-metrics samples, run.json keeps 1,038 executor NVTX ranges, 34,140 kernels and 5,196 copies. Not imported today: 2,714 other NVTX ranges and marks, 21,136 CUDA runtime calls (kept only as a launch-name attribute), 17,735 OSRT calls (including the ZMQ send/recv), 432 memsets, 2,796 synchronizations, 2,301 CUDA events, 1,786 graph-node events, 50 profiler-overhead ranges, 42 diagnostic messages, and every GPU-metrics sample. Observed
  3. Code run 0ac2db: 18,093 PyTorch-profiler spans carry no process or thread. trace/torch_trace.json has pid/tid on every event and adapters/torch_trace.py uses tid internally, but it does not write them to the span. Observed
  4. Host PIDs are mostly Unavailable. Nsight and the component stamps record PIDs in the server container's namespace (211, 403; 1, 304). Docker's State.Pid in topology.json gives the host PID of the container's PID 1 only; in the timeline run PID 1 is nsys, so the host PIDs of trtllm-serve and the worker are not recorded anywhere. Observed
  5. Engine-record spans have no process. queue (executor pickup), first_scheduled_time, prefill (iteration 66) and the other /perf_metrics-derived spans name no PID or thread, so a lane view cannot place them without a rule. Observed
  6. Small Nsight quirks a v2 importer must handle: CUDA events on stream 4294967295 (−1 stored unsigned); 4 NVTX domain events whose globalTid decodes to PID 0; 14 NVTX rows with no end (marks, categories) and some starting before the session (negative times). Observed
  7. The stamp pairing is by order, not by a message id. ZMQ send → receive links (130 in the components run) pair the k-th send with the k-th receive of the same request Calculated; the OSRT send/recv calls in Nsight carry no id at all, so they can be paired only by time Inferred.

Files and how to rerun

Scripts (this folder, run with /mnt/ie-data/venvs/cc-v2-proto/bin/python, in order):

  • canonical.py — full import of the five runs into canonical events, samples, links and profiles (Parquet).
  • synth.py — the synthetic set (prints its rule and counts); synth.py --subset — the 10 % subset.
  • stores.py <A|B|C|D> <real|synthetic|synthetic10> — build one store; the four options and the shared query API.
  • bench.py <dataset> <options…>, live.py, perfetto_check.py <datasets…> — measurements.
  • collect.py — writes results.json (this page's only data).

Data (bulk, not in the repository): /mnt/ie-data/cc-v2-proto/ — canonical/, stores/{real,synthetic,synthetic10}/, bench/, live/, logs/, bin/trace_processor_shell, deps/ (dependency-size probes).
